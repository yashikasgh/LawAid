1. Project Overview
LawAid is a privacy-first AI legal platform that bridges the gap between citizens, police officers, and legal
professionals. India's 2023 transition from IPC to BNS (Bharatiya Nyaya Sanhita) created mass confusion —
FIRs are being filed with wrong sections, victims cannot understand legal documents, and legal guidance
remains inaccessible. LawAid solves this using a locally-hosted LLM (Llama 3.1 via Ollama) combined with
Retrieval-Augmented Generation (RAG) over the full BNS corpus.
Citizens / Victims
File complaints, understand FIRs, get plain-language legal guidance and next steps
Police Officers
Intake victim statements via voice or text, validate BNS sections, generate and authenticate
FIRs
Lawyers
Analyse case documents, build timelines, research precedents, draft petitions
Legal Aid Orgs
Access dashboards, manage multiple citizen cases, generate bulk reports
All AI processing runs locally via Ollama — no data leaves the server. This is critical for police stations handling
sensitive victim information.

2. Citizen Module — Feature Execution
2A. File a Complaint & Get Guidance
The citizen describes an incident in natural language. The system extracts facts, recommends applicable BNS
sections, explains them simply, and suggests concrete next steps — it does NOT generate the FIR (that is the
police's role). This keeps legal responsibility correctly placed.
1
Complaint Input
User types or pastes their incident description in any language (Hindi, English, Marathi, etc.). The
interface is a simple chat — no forms, no legal knowledge required.
Tech: Next.js chat UI · FastAPI /complaint endpoint · IndicTrans2 for non-English inputs
2
Text Preprocessing
Raw input is cleaned — noise removed, language detected, translated to English if needed. Spell
correction applied for informal writing.
Tech: LangChain text splitter · IndicBERT language detection · IndicTrans2 translation
3
Named Entity Recognition (NER)
AI extracts structured facts: time, location, parties involved, type of offence, objects (weapon,
vehicle, money), and relationship between parties.
Tech: spaCy NER + custom legal entity model · LangChain extraction chain · Llama 3.1
4
BNS Section Retrieval via RAG
Extracted entities become a semantic query. The vector database (pre-loaded with all BNS
sections) returns the top-K most relevant sections ranked by similarity score.
Tech: ChromaDB vector store · sentence-transformers/all-MiniLM-L6-v2 embeddings · BM25 hybrid search
5
Cross-Encoder Reranking
A reranker model re-scores the retrieved sections for precision before presenting to the user. This
eliminates false positives — a critical step for legal accuracy.
Tech: cross-encoder/ms-marco-MiniLM-L12-v2 · LangChain reranker wrapper
6
Plain-Language Explanation
Llama 3.1 receives the top sections + extracted facts and generates a citizen-friendly explanation
of what each section means in their context.
Tech: Ollama / Llama 3.1 · LangChain prompt template · FastAPI streaming response

7
Next Steps & Action Guidance
The system presents a clear action plan: which police station to visit, free legal aid contacts
(DLSA), helpline numbers (112/1091), what documents to carry, and what to expect.
Tech: Template-based response engine · PostgreSQL legal aid directory · FastAPI response
2B. Understand an Existing FIR
A citizen uploads a scanned FIR image or PDF. The system extracts text, identifies legal sections, explains each
one in plain language, and informs the citizen of their rights and what they can do next.
1
Document Upload
Citizen uploads a photo, scan, or PDF of their FIR through the web or mobile interface. File size
and format are validated immediately.
Tech: Next.js file upload component · FastAPI multipart endpoint · MongoDB GridFS for storage
2
OCR Extraction
The uploaded image or PDF is passed through OCR to extract all textual content. For typed FIRs,
EasyOCR handles the primary extraction.
Tech: EasyOCR (primary) · PyMuPDF for PDFs · TrOCR for handwritten FIRs (future improvement)
3
Section Detection
Regex + NLP patterns identify BNS/IPC section numbers within the extracted text. The system
maps old IPC references to their BNS equivalents automatically.
Tech: SpaCy pattern matching · Custom regex · IPC-to-BNS mapping table in PostgreSQL
4
RAG Retrieval for Each Section
For each detected section number, the system retrieves the full legal text and explanation from the
vector database.
Tech: ChromaDB · Direct section ID lookup + semantic fallback · LangChain retrieval chain
5
Plain-Language Summary
Llama 3.1 generates a citizen-friendly summary of the entire FIR — what the charges mean,
severity level, and what the complainant should expect.
Tech: Ollama / Llama 3.1 · Structured prompt template · LangChain output parser
6
Rights & Next Steps
The system displays a rights card: right to FIR copy (zero cost), right to legal representation, bail
eligibility, free legal aid access, and escalation options.
Tech: Template-based rights engine · DLSA directory API · FastAPI response

3. Police Officer Module — Feature Execution
The police module is the most critical flow in LawAid. A victim walks in, narrates their incident (in any language,
via voice or text), and the system guides the constable through section validation, FIR generation, and secure
authentication — reducing both drafting errors and the IPC-to-BNS conversion mistakes that are rampant
post-2023.
1
Login & Role Verification
The constable logs into LawAid using their badge number and password. JWT token issued.
Role-based access ensures constables only see complaint intake while senior officers see full FIR
management.
Tech: FastAPI JWT auth · PostgreSQL user/role tables · bcrypt password hashing
2
Victim Statement Intake — Voice or Text
The constable opens a new complaint. The victim can either speak directly into a microphone
(speech-to-text) or the constable types as the victim narrates. Supports Hindi, Marathi, English, and
all major Indian languages.
Tech: OpenAI Whisper (local deployment via faster-whisper) · IndicASR as fallback · React mic API · FastAPI
WebSocket for streaming
3
AI Extracts Key Facts from Statement
The transcribed or typed statement is processed by an NER pipeline that extracts: complainant
name, accused details, date/time, location, offence type, financial amounts, weapons/vehicles
used, and witness information.
Tech: spaCy + custom legal NER model · LangChain extraction chain · Llama 3.1 for complex extractions ·
FastAPI structured response
4
BNS Sections Suggested + Explained
Based on extracted facts, the RAG engine retrieves the most relevant BNS sections. Each section
is displayed with: the section number, its legal title, a plain-language explanation of why it applies to
this specific incident, and the applicable punishment range.
Tech: ChromaDB hybrid search · cross-encoder reranker · Llama 3.1 for contextual explanation · LangChain
RAG chain
5
Constable Reviews & Validates Sections
The constable sees each recommended section with full explanation. They can accept, reject, or
add sections manually. This keeps human judgment in the loop — the system assists but never
decides.
Tech: Next.js review UI with accept/reject controls · FastAPI PATCH /draft endpoint · Section audit trail in
MongoDB

6
FIR Draft Generation & Constable Confirmation
Using the validated sections and extracted facts, Llama 3.1 generates a complete, formatted FIR
draft. The constable reviews the full draft, can edit any field, and then formally confirms it. A senior
officer digital signature can optionally be required.
Tech: Llama 3.1 + structured FIR prompt template · PyMuPDF for PDF generation · React editable draft view ·
FastAPI PUT /fir/confirm
7
Unique FIR ID + Digital Authentication + Audit Log
On confirmation: a unique FIR ID (format: FIR/STATE/YEAR/STATION/SERIAL) is assigned.
SHA-256 hash of the document is computed and stored. Timestamp, officer ID, and station details
are locked. Any future edit creates a new version with the edit logged. Full immutable audit trail
maintained.
Tech: UUID + sequential ID generator · Python hashlib SHA-256 · PostgreSQL audit_logs table · MongoDB for
FIR versions · PDF stamped with QR code linking to verification endpoint
FIR ID Format
Each FIR receives a structured unique identifier that encodes all key metadata:
FIR / MH / 2026 / PS001 / 04821
Type State Year Station Code Serial No.

4. Lawyer Module — Feature Execution
Lawyers upload case documents and use LawAid as an intelligent research and drafting assistant. The system
builds case timelines, surfaces relevant legal precedents, and assists in drafting petitions — compressing hours
of manual work into minutes.
1
Document Upload & Parsing
Lawyer uploads multiple documents at once: FIRs, charge sheets, witness statements, evidence
files (PDF, images, DOCX). The system queues and processes them in parallel.
Tech: Next.js multi-file upload · FastAPI background tasks · PyMuPDF + PDFPlumber for parsing · MongoDB
GridFS for storage
2
AI Fact Extraction & Case Timeline
The system reads all documents and extracts dated events, parties, locations, financial figures, and
key facts. These are arranged into a chronological case timeline automatically.
Tech: LangChain document chain · Llama 3.1 timeline extraction · spaCy date/entity NER · React timeline
component
3
Legal Precedent Research via RAG
The extracted facts are used to query a vector database loaded with Supreme Court and High
Court judgements. The system surfaces the most factually similar cases with their outcomes.
Tech: ChromaDB · Sentence Transformers · Legal judgement dataset (IndianKanoon corpus) · Cross-encoder
reranker
4
AI-Assisted Petition Drafting
The lawyer uses a guided drafting interface. Llama 3.1 auto-inserts relevant BNS sections, case
citations, and argument structures based on the case facts.
Tech: Llama 3.1 · LangChain drafting chain · React rich text editor · Auto-citation from RAG results
5
Case Summary & Export
A complete case package is generated: executive summary, full timeline, charges, precedents, and
draft petition. Exported as a structured, printable PDF.
Tech: ReportLab PDF generation · PyMuPDF · FastAPI /export endpoint · SHA-256 document hash
5. AI & Infrastructure Layer
5A. RAG Pipeline — How It Works
Step 1: Indexing (one-time): All BNS sections, legal acts, and case law are converted to embeddings using
sentence-transformers and stored in ChromaDB with metadata (section number, chapter, act name).

Step 2: Query Processing: User query → language detection → translation if needed → semantic embedding
generated.
Step 3: Hybrid Retrieval: Semantic search (vector similarity) + BM25 keyword search run in parallel. Results
merged and deduplicated.
Step 4: Reranking: Cross-encoder model re-scores top-20 results → top-5 selected. This is the critical quality
step.
Step 5: Context Assembly: Retrieved sections assembled into a structured context block with metadata and
passed to Llama 3.1.
Step 6: Generation + Citation: Llama 3.1 generates response grounded in retrieved context. Response
includes section citations. Confidence score computed.
Step 7: Guardrail Check: If confidence < threshold, system adds a disclaimer. Never fabricates section
numbers.

5C. Security Architecture
JWT Auth
Issued on login, 8-hour expiry, refresh token stored in HttpOnly cookie
RBAC
4 roles: Citizen, Constable, Officer, Lawyer — each with scoped API permissions
Document Hash
SHA-256 of every generated FIR stored in PostgreSQL. Any edit detected by hash mismatch.
Audit Log
Every action (login, view, edit, confirm, download) logged with user ID + timestamp + IP.
Encryption
Sensitive fields (Aadhaar, phone) encrypted at rest with AES-256. Passwords hashed with
bcrypt.
DPDPA 2023
Data minimisation, explicit consent on complaint submission, right to erasure endpoint built
in.
